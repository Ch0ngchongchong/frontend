# 딱 재고 · Next.js

## 로컬 실행

`npm install` 후 `npm run dev`로 개발 서버(`http://localhost:3000`)를 실행합니다. 프로덕션은 `npm run build` 후 `npm start`로 실행합니다. Vercel 프로젝트의 프레임워크를 Next.js로 설정하고 기존 Vite의 출력 디렉터리(`dist`) 오버라이드를 해제하세요. 정적 파일만 배포하는 호스팅은 SSR·ISR을 실행할 수 없습니다.

브라우저의 `/api/*` 요청은 `next.config.js`의 rewrite로 배포 백엔드에 전달됩니다. 백엔드 주소는 이 파일에서 변경합니다. 로컬 백엔드를 별도로 실행할 필요는 없습니다.

API 요청은 로그인 구현 전까지 임시 헤더 `X-User-Id: 1`을 사용합니다. 백엔드 DB에 해당 사용자가 있어야 합니다. 상품, 발주 작성·조회·승인·전달·취소, 명세서 업로드·판독 폴링, 입고 줄 수정·확정, 재고 조회는 `api/` 명세에 연결됩니다. 거래처는 아래 계약으로 서버를 요청하며 API가 없으면 빈 목록을 표시합니다. 달력·변경 이력·사장 승인/반려는 아직 실제 API가 없는 시안입니다.

## 렌더링 전략

| 경로 | 전략 | 이유 |
| --- | --- | --- |
| `/` | SSG + 클라이언트 상호작용 | 빌드 시 홈 HTML 생성, 지도 드래그·팝오버는 hydration 후 동작 |
| `/suppliers`, `/suppliers/[id]` | CSR·SWR 메모리 캐시 | 거래처 API 조회. 동적 ID 직접 접근 지원, 샘플·로컬 저장 없음 |
| `/products`, `/orders` | 정적 화면 틀 + CSR·SWR 메모리 캐시 | 화면 이동은 백엔드 응답을 기다리지 않음. 재방문 시 기존 목록을 즉시 표시하고 백그라운드 갱신 |
| `/upload`, `/inspection`, `/approval`, `/calendar`, `/history`, `/profile` | CSR (공통 프레임은 사전 렌더링) | 사진·브라우저 저장소·입력·스크롤 중심 화면은 클라이언트에서 로드 |

모든 화면은 URL로 직접 접근·새로고침·뒤로가기가 가능합니다. 프로필은 공통 앱 상태로 유지합니다. 검수 대상은 `/inspection?id=검수ID`로 지정합니다. 상품 저장 후 목록 갱신 및 발주 한도 편집은 CSR입니다.

상품·발주는 사용자 데이터 없는 HTML을 정적 생성합니다. 데이터는 브라우저 메모리의 사용자 ID별 SWR 캐시에만 보관하고, 재진입·창 포커스 복귀 시 재검증합니다. 상품 저장 성공 응답은 즉시 캐시에 반영합니다. 첫 조회나 전체 새로고침에는 데이터 대기가 필요하지만 재방문에서는 기존 목록을 유지하며 갱신합니다. 백그라운드 조회 실패도 기존 목록을 지우지 않습니다. 현재 사용자 ID는 임시값 `1`이며 실제 로그인 연결 시 캐시 키와 요청 헤더를 함께 변경해야 합니다.

상품 목록은 전체 너비로 표시하며 등록 폼은 기본적으로 숨깁니다. 목록의 `상품 등록` 또는 상품 행의 `수정`을 누르면 목록 아래에 폼이 열리고, 저장·취소·닫기 시 다시 숨겨집니다.

발주 한도는 샘플·로컬 저장 없이 서버를 사용합니다. 프런트엔드에서 사용하는 계약은 `GET/POST /purchase-order-limits`, `PATCH/DELETE /purchase-order-limits/{id}`이며, 항목은 `{ id, product, limit, unit }`, 생성·수정 본문은 `{ product, limit, unit }`입니다. GET은 배열, POST/PATCH는 저장된 항목, DELETE는 204를 반환해야 합니다. `X-User-Id: 1`로 매장을 구분합니다. 현재 배포 백엔드에는 이 API가 없어 조회 실패 시 0개로 표시하며, 저장·삭제 실패는 오류로 알리고 화면 데이터는 변경하지 않습니다. 실제 서버 저장을 사용하려면 백엔드에 이 계약 구현 및 배포가 필요합니다.

거래처 계약은 `GET/POST /suppliers`, `PATCH/DELETE /suppliers/{id}`입니다. GET은 배열, POST/PATCH는 저장된 객체, DELETE는 204를 반환합니다. 필드는 `{ id, name, category, deliveryDays, orderCutoff, since }`이며 생성·수정에는 id를 제외합니다. 이름은 필수, 나머지 입력은 선택이며 since는 날짜 문자열입니다. 현재 배포 API에는 이 경로가 없어 오류와 빈 목록을 표시하고 저장 실패 시 입력을 유지합니다. 서버 성공 후에만 목록·홈 지도·연결 건수를 갱신합니다. 샘플 거래처·가짜 품목·주문 일정은 표시하지 않습니다.

발주 작성의 `상품 추가`는 입력 행을 추가하고 `−`는 해당 행을 삭제합니다(최소 1행 유지). 등록 상품 ID와 1 이상의 정수 수량으로 저장합니다. API는 단위를 받지 않으므로 기준 단위 수량만 전송합니다. 승인·전달·취소 후 목록과 상태별 건수를 갱신하고, 전달 완료 시 새 검수 건을 조회합니다.

명세서 업로드는 JPG·PNG·HEIC·PDF 및 데모용 TXT를 최대 10MB까지 받으며 `multipart/form-data`의 `file` 필드로 전송합니다. 판독 중에만 1.5초 간격으로 상태를 조회합니다. 입고 확인에서 서버의 초안·후보·누락 줄을 보고 상품과 수량을 저장하며, 서버 `check_count`가 0인 직원 확인 대기 건만 확정할 수 있습니다. 모두 일치하면 재고 반영, 불일치하면 사장 승인 대기로 처리되며 서버 응답을 기준으로 표시합니다. 원본 다운로드·예외 사유·추가 사진 저장 API는 없어 해당 정보를 서버에 저장한 것처럼 표시하지 않습니다. 현재 백엔드 OCR은 데모 구현이므로 사진·PDF를 실제 판독하는 서비스와는 다릅니다.

입고 확인의 검수 선택은 다른 영역과 동일한 카드·제목·건수 칩·입력 테두리를 사용합니다. 키보드로 조작 가능한 기본 선택 목록을 유지하며, 목록을 불러오는 중이거나 검수 건이 없으면 선택을 비활성화합니다.

백엔드의 `/openapi.json`에서 API 명세를 확인할 수 있습니다. 상품 조회가 `500`을 반환하면 백엔드의 Vercel 함수 로그와 DB 연결·환경변수·사용자 데이터를 확인해야 합니다.
