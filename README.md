# 딱 재고 · Next.js

## 로컬 실행

`npm install` 후 `npm run dev`로 개발 서버(`http://localhost:3000`)를 실행합니다. 프로덕션은 `npm run build` 후 `npm start`로 실행합니다. Vercel 프로젝트의 프레임워크를 Next.js로 설정하고 기존 Vite의 출력 디렉터리(`dist`) 오버라이드를 해제하세요. 정적 파일만 배포하는 호스팅은 SSR·ISR을 실행할 수 없습니다.

브라우저의 `/api/*` 요청은 `next.config.js`의 rewrite로 배포 백엔드에 전달됩니다. 백엔드 주소는 이 파일에서 변경합니다. 로컬 백엔드를 별도로 실행할 필요는 없습니다.

API 요청은 로그인한 계정의 사용자 ID를 `X-User-Id` 헤더로 보냅니다(아래 '로그인·역할별 메뉴'). 백엔드 DB에 해당 사용자가 있어야 합니다. 상품, 발주 작성·조회·승인·전달·취소, 명세서 업로드·판독 폴링, 입고 줄 수정·확정, 재고 조회는 `api/` 명세에 연결됩니다. 거래처는 아래 계약으로 서버를 요청하며 API가 없으면 빈 목록을 표시합니다. 달력·변경 이력·사장 승인/반려는 아직 실제 API가 없는 시안입니다.

## 렌더링 전략

| 경로 | 전략 | 이유 |
| --- | --- | --- |
| `/login` | SSG | 역할 선택 화면. 로그인 상태면 원래 보려던 화면이나 역할별 첫 화면으로 이동 |
| `/` | SSG + 클라이언트 상호작용 | 사장님 첫 화면. 빌드 시 홈 HTML 생성, 지도 드래그·팝오버는 hydration 후 동작 |
| `/staff` | CSR | 직원 첫 화면(오늘 할 일). 휴대폰용 |
| `/suppliers`, `/suppliers/[id]` | CSR·SWR 메모리 캐시 | 거래처 API 조회. 동적 ID 직접 접근 지원, 샘플·로컬 저장 없음 |
| `/products`, `/orders` | 정적 화면 틀 + CSR·SWR 메모리 캐시 | 화면 이동은 백엔드 응답을 기다리지 않음. 재방문 시 기존 목록을 즉시 표시하고 백그라운드 갱신 |
| `/upload`, `/inspection`, `/approval`, `/calendar`, `/history`, `/profile` | CSR (공통 프레임은 사전 렌더링) | 사진·브라우저 저장소·입력·스크롤 중심 화면은 클라이언트에서 로드 |

모든 화면은 URL로 직접 접근·새로고침·뒤로가기가 가능합니다. 로그인 상태는 브라우저에서만 알 수 있어, 사전 렌더링된 HTML은 로그인 확인 중 화면이고 hydration 뒤 실제 화면을 그립니다. 프로필은 공통 앱 상태로 유지합니다. 검수 대상은 `/inspection?id=검수ID`로 지정합니다. 상품 저장 후 목록 갱신 및 발주 한도 편집은 CSR입니다.

상품·발주는 사용자 데이터 없는 HTML을 정적 생성합니다. 데이터는 브라우저 메모리의 사용자 ID별 SWR 캐시에만 보관하고, 재진입·창 포커스 복귀 시 재검증합니다. 상품 저장 성공 응답은 즉시 캐시에 반영합니다. 첫 조회나 전체 새로고침에는 데이터 대기가 필요하지만 재방문에서는 기존 목록을 유지하며 갱신합니다. 백그라운드 조회 실패도 기존 목록을 지우지 않습니다. 캐시 키와 요청 헤더에는 로그인한 사용자 ID가 들어가 계정을 바꿔도 데이터가 섞이지 않으며, 로그아웃하면 메모리 캐시와 판독 알림을 지웁니다.

상품 목록은 전체 너비로 표시하며 등록 폼은 기본적으로 숨깁니다. 목록의 `상품 등록` 또는 상품 행의 `수정`을 누르면 목록 아래에 폼이 열리고, 저장·취소·닫기 시 다시 숨겨집니다.

발주 한도는 샘플·로컬 저장 없이 서버를 사용합니다. 프런트엔드에서 사용하는 계약은 `GET/POST /purchase-order-limits`, `PATCH/DELETE /purchase-order-limits/{id}`이며, 항목은 `{ id, product, limit, unit }`, 생성·수정 본문은 `{ product, limit, unit }`입니다. GET은 배열, POST/PATCH는 저장된 항목, DELETE는 204를 반환해야 합니다. `X-User-Id: 1`로 매장을 구분합니다. 현재 배포 백엔드에는 이 API가 없어 조회 실패 시 0개로 표시하며, 저장·삭제 실패는 오류로 알리고 화면 데이터는 변경하지 않습니다. 실제 서버 저장을 사용하려면 백엔드에 이 계약 구현 및 배포가 필요합니다.

발주 한도 경고(US-01 R7): 한 발주 안에서 같은 상품의 수량을 합쳐 한도와 비교합니다. 한도는 상품명과 단위가 상품의 이름·기준 단위와 모두 같을 때만 적용됩니다. 발주 작성 중에는 수량을 넣은 줄 아래에 경고하고, 발주 초안의 `승인`을 누르면 초과 상품·수량을 경고 창으로 보여 준 뒤 `확인했어요, 승인`을 눌러야 승인 요청을 보냅니다. 서버는 한도를 검사하지 않으며, 한도 조회에 실패하면 경고 없이 승인됩니다.

거래처 계약은 `GET/POST /suppliers`, `PATCH/DELETE /suppliers/{id}`입니다. GET은 배열, POST/PATCH는 저장된 객체, DELETE는 204를 반환합니다. 필드는 `{ id, name, category, deliveryDays, orderCutoff, since }`이며 생성·수정에는 id를 제외합니다. 이름은 필수, 나머지 입력은 선택이며 since는 날짜 문자열입니다. 현재 배포 API에는 이 경로가 없어 오류와 빈 목록을 표시하고 저장 실패 시 입력을 유지합니다. 서버 성공 후에만 목록·홈 지도·연결 건수를 갱신합니다. 샘플 거래처·가짜 품목·주문 일정은 표시하지 않습니다.

발주 작성의 `상품 추가`는 입력 행을 추가하고 `−`는 해당 행을 삭제합니다(최소 1행 유지). 등록 상품 ID와 1 이상의 정수 수량으로 저장합니다. API는 단위를 받지 않으므로 기준 단위 수량만 전송합니다. 승인·전달·취소 후 목록과 상태별 건수를 갱신하고, 전달 완료 시 새 검수 건을 조회합니다.

명세서 업로드는 JPG·PNG·HEIC·PDF 및 데모용 TXT를 최대 10MB까지 받으며 `multipart/form-data`의 `file` 필드로 전송합니다. 판독 중에만 1.5초 간격으로 상태를 조회합니다. 입고 확인에서 서버의 초안·후보·누락 줄을 보고 상품과 수량을 저장하며, 서버 `check_count`가 0인 직원 확인 대기 건만 확정할 수 있습니다. 모두 일치하면 재고 반영, 불일치하면 사장 승인 대기로 처리되며 서버 응답을 기준으로 표시합니다. 명세서 원본 다운로드 API는 없습니다.

예외 사유·사진·직원 동작(US-04·US-06): 발주와 다른 건(`all_match`가 false)은 서버가 사유 없이 확정하지 않으므로, 입고 확인의 확정 카드에서 `예외 사유`를 필수로 받아 `POST /inspections/{id}/confirm`에 `{ reason }`으로 보냅니다. 예외 사진은 `직원 확인 대기`에서만 `POST /inspections/{id}/exception-photos`(`multipart/form-data`의 `file`, JPG·PNG·HEIC, 10MB 이하, 여러 장은 한 장씩 차례로)로 올리고, `GET /inspections/{id}/exception-photos`로 목록을, `GET /inspections/{id}/exception-photos/{photo_id}`로 원본을 받습니다. 원본은 `X-User-Id` 헤더가 필요해 직접 받아 임시 주소로 보여 주며, 브라우저가 그리지 못하는 HEIC는 파일 받기 링크로 대신합니다. 사진은 검수 건에 연결되어 예외 승인 화면에서 선택한 건의 사진만 보입니다. `사장 승인 대기` 건은 `확정 취소`(`POST /inspections/{id}/cancel-confirmation`), `반려` 건은 반려 사유와 함께 `재검수 시작`(`POST /inspections/{id}/reinspect`)을 보여 주며, 둘 다 `직원 확인 대기`로 돌아가고 지난 예외 사유를 이어서 고칠 수 있습니다. 서버가 이 두 동작을 직원 계정에게만 허용하므로 직원으로 로그인했을 때만 버튼을 보여 주고, 사장님에게는 직원 계정에서 할 수 있다는 안내를 보여 줍니다. 현재 백엔드 OCR은 데모 구현이므로 사진·PDF를 실제 판독하는 서비스와는 다릅니다.

판독 줄 추가(US-04): 입고 확인의 `+ 판독에 없는 줄 추가`로 `직원 확인 대기` 건에 판독에서 빠진 줄을 직원이 명세서를 보고 추가합니다. 계약은 `POST /inspections/{id}/lines`이고 본문은 `{ name, product_id, quantity, unit, unit_price }`입니다. name은 필수이고 나머지는 null일 수 있으며, quantity는 1 이상, unit_price는 0 이상의 정수입니다. 응답은 갱신된 검수 건 전체입니다. 서버는 입력값을 판독값(`read`)과 확인값에 함께 저장하고, 그 줄에 `source: "staff"`를 붙이며, 변경 이력에 kind `직원 줄 추가`(new_value: `line_id, line_no, name, product_id, quantity, unit, unit_price`)를 남기는 것으로 가정합니다. 화면은 `source`가 `staff`인 줄과 이 이력을 "직원이 추가한 줄"로 표시합니다. 추가 폼이 열려 있으면 확정할 수 없습니다. 현재 배포 백엔드에는 이 경로가 없어 오류를 폼 안에 표시하고 입력을 유지합니다.

불확실한 값·규칙 검증 실패 강조(US-03·US-04): 입고 확인 표의 `명세서 원본 값` 칸에서 판독값(`read`)을 보고 화면이 직접 고릅니다. 서버는 아직 이 정보를 보내지 않습니다. 불확실한 값은 줄의 선택 필드 `uncertain_fields`(읽은 값 필드 이름 배열, 예: `["quantity", "unit_price"]`. 서버가 보내면 사용)와 OCR이 읽지 못해 비어 있는 수량·단가·금액(직원이 추가한 줄 제외)이며, 주황 바탕 칸에 해당 값을 테두리로 짚고 "확인 필요 · 이유"를 적습니다. 수량이 불확실하면 `확인 수량` 칸도 강조합니다. 규칙 검증은 읽은 수량 × 단가 ≠ 금액만 검사하며, 빨강 바탕 칸에 "규칙 검증 실패 · 계산식"을 적습니다. 줄 금액 합 ≠ 합계(서버가 명세서 합계를 보내지 않음)와 OCR 글자에 없는 숫자(OCR 원문을 보내지 않음)는 아직 검사하지 않습니다. 강조는 알리기만 하고 확정을 막는 기준은 서버의 `check_count`입니다.

판독 완료 알림(US-03): 서버 알림 API 없이 화면에서 처리합니다. 모든 화면에서 검수 목록을 조회해, `판독 중`이던 건이 `직원 확인 대기`가 되면 완료, `업로드 대기`로 돌아가면 실패 알림을 화면 아래에 띄우고 위쪽 바의 알림 목록에 남깁니다. 완료 알림은 `/inspection?id=검수ID`, 실패 알림은 `/upload?id=검수ID`로 이동하며 업로드 화면은 `?id`의 건을 선택합니다. 알림은 이 탭의 메모리에만 있어 새로고침하면 사라지고, 화면을 열기 전이나 탭이 닫혀 있을 때 끝난 판독은 알리지 못합니다. 이를 위해 어느 화면이든 열 때 검수 목록을 한 번 조회합니다.

판독 정확도(US-07, 03 3-4 측정과 기록): 변경 이력 화면에서 고른 검수 건의 판독 정확도를 보여 줍니다. 서버가 지표를 보내지 않아 `GET /inspections/{id}/history`의 `changes`(`{ id, changed_by, changed_at, action, field, old_value, new_value }`, 값은 문자열이고 숫자·객체는 JSON 문자열)로 화면에서 계산합니다. 판독 줄은 `판독`·`line N` 기록 수, 직원이 고친 칸은 `줄 수정`·`line N 칸이름` 기록에서 그 칸의 첫 이전 값(판독이 채운 값)과 마지막 새 값이 다른 경우입니다(고쳤다가 되돌리면 맞은 것으로 봄). 필드별 정확도는 품목(`product_id`)·수량·단위만 계산합니다. 단가·금액은 직원이 고칠 수 없어 이력에 정답이 남지 않으므로 재지 않습니다. 직원이 고친 줄 비율(목표 10% 이하, 넘으면 강조), 행 누락률(`직원 줄 추가`·`line N` 기록 ÷ 전체 줄. 서버에 줄 추가가 아직 없어 지금은 0%), 업로드(`업로드`·`document`)부터 마지막 확정(`확정`·`status`)까지 걸린 시간을 함께 보여 줍니다. 명세서를 다시 올리면 그 뒤 판독부터 새로 세고, 확정 취소·재검수로 `직원 확인 대기`가 되면 확정 전(값이 바뀔 수 있음)으로 표시합니다. 판독 기록이 없는 건은 계산할 수 없다고 표시합니다.

입고 확인의 검수 선택은 다른 영역과 동일한 카드·제목·건수 칩·입력 테두리를 사용합니다. 키보드로 조작 가능한 기본 선택 목록을 유지하며, 목록을 불러오는 중이거나 검수 건이 없으면 선택을 비활성화합니다.

백엔드의 `/openapi.json`에서 API 명세를 확인할 수 있습니다. 상품 조회가 `500`을 반환하면 백엔드의 Vercel 함수 로그와 DB 연결·환경변수·사용자 데이터를 확인해야 합니다.

로그인·역할별 메뉴(client-meeting-2 피드백 7·8): 서버에 로그인 API가 없어 `/login`에서 시드 계정(사장님 `1`, 같은 매장 직원 `2`)을 고르면 그 사용자 ID를 이 브라우저의 `localStorage`(`ddakjaego-session`)에 저장하고 모든 요청의 `X-User-Id`로 보냅니다. 비밀번호 확인이 없는 시험용 로그인이며, 실제 인증은 서버에 로그인 API가 생긴 뒤 바꿔야 합니다. 로그인하지 않으면 모든 화면이 `/login?next=원래 경로`로 이동하고, 로그인 후 그 경로가 해당 역할이 열 수 있는 화면이면 돌아갑니다. 사장님은 8개 화면을 모두, 직원은 명세서 업로드·입고 확인만 메뉴에 보며, 직원이 다른 화면 주소로 들어오면 "사장님만 볼 수 있어요" 안내를 보여 줍니다. 권한의 최종 판단은 서버입니다(발주 승인·전달·취소, 검수 승인·반려·종료, 변경 이력은 사장님만 / 확정 취소·재검수는 직원만). 프로필은 계정별로 저장하며, 로그인 전 프로필은 사장님 계정 것으로 이어 씁니다. 마이페이지에서 로그아웃합니다.

직원 휴대폰 화면(client-meeting-2 피드백 6·9): 직원으로 로그인하면 첫 화면이 `/staff`(오늘 할 일)이며, 위쪽 탭 대신 엄지가 닿는 아래 탭(오늘 할 일·명세서 촬영·입고 확인·내 정보)을 쓰고 본문을 휴대폰 폭(최대 640px) 한 줄로 놓습니다. 오늘 할 일은 검수 건을 `지금 확인할 입고`(직원 확인 대기·반려), `명세서를 올릴 입고`(업로드 대기), `기다리는 중`(판독 중·사장 승인 대기)으로 나눠 누르면 해당 건의 입고 확인·업로드로 바로 갑니다. 수량·단가 입력칸은 숫자 키패드(`inputMode="numeric"`)를 띄우고, 화면 폭 767px 이하에서는 입고 확인 표를 가로로 밀지 않고 줄마다 카드로 쌓습니다(사장님이 좁은 화면에서 볼 때도 같음). 판독 알림은 아래 탭 위로 띄웁니다.

발주 복사(client-meeting-2 피드백 15): 공급처마다 전화·문자·카카오톡으로 받는 방식이 달라 자동 전송 대신 붙여 넣기용 글을 만듭니다. 승인한 발주(`발주 확인 완료` 이후, 취소 제외)는 목록 행의 `복사`와 상세의 `발주 내용 복사`로 매장 이름, 발주 번호, 공급처, 상품별 수량(같은 상품은 합침, 상품의 기준 단위·규격 사용), 프로필 연락처(있으면)를 클립보드에 넣습니다. 상세에서 복사될 글을 미리 볼 수 있으며, `발주 초안`은 승인 뒤에 복사하라고 안내합니다. 클립보드 API가 막히면 선택 후 복사 방식으로 다시 시도하고, 그래도 실패하면 미리보기를 직접 복사하라고 알립니다.
